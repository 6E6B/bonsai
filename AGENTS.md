# Agent rules

Read this at the start of every session. Other docs are in `docs/`; what's left to build is in `docs/gaps.md`.

## Layout

```
crates/
  bonsai-api/     Roblox API client. The only crate that touches the network.
  bonsai-core/    Domain logic: accounts, store, cache, commands, background jobs.
  bonsai-codegen/ Generates bonsai-api wrappers from specs (`cargo xtask codegen`).
  bonsai-plugin/  Plugin manifests and the Luau sandbox. No network, no store. See docs/plugins.md.
  bonsai/         Tauri 2 shell. Wires bonsai-core to the UI. No domain logic.
    src/ipc.rs      Typed commands and events (tauri-specta).
    src/notify.rs   Batches store changes into one `storeChanged` event per frame.
    src/thumb.rs    `thumb://` protocol serving thumbnails from bonsai-core.
    ui/             SolidJS app (Vite, TypeScript, Tailwind v4, bun).
      src/app/          Shell: providers, router, layout.
      src/features/<x>/ One folder per screen or area.
      src/lib/ipc/      Generated bindings. Never edit.
      src/lib/commands/ UI side of the command registry and shortcut handling.
      src/lib/ui/       Our Kobalte components and theme tokens. See its README.md.
      src/lib/store.ts  Mirror of bonsai-core state.
```

## Before you write code

- Work only inside the area you were given.
- Look up every endpoint you need in `vendor/roblox-api-tracker/<host>/v*.json`. Prefer the highest version that is not `deprecated: true`.
- If the endpoint is not there, check `specs/undocumented/`. If it is not there either, capture the request from roblox.com in browser devtools and add a spec (see below). Never guess a URL or a field name.

## Hard rules

### Network and secrets

- No network calls outside `crates/bonsai-api`. The webview never fetches anything remote: no CDNs, no Google Fonts, no Roblox image URLs. The CSP in `tauri.conf.json` enforces this; don't loosen it.
- No hardcoded endpoint URLs outside generated code and `specs/undocumented/`.
- Never edit files under `crates/bonsai-api/src/generated/`. Change the spec or the generator and rerun `cargo xtask codegen`.
- Never log, print, commit or write to disk a `.ROBLOSECURITY` cookie, auth ticket or CSRF token. Redact them in `Debug` impls. Never send one to the UI.
- Never auto-solve captchas or bypass a challenge. Surface it to the user.

### User actions

- No automated purchases, trades, friend requests or messages in Bonsai's own code. Every write it makes is a direct result of a user click or keypress.
- Plugins are the one exception: they may write without a click only through the tiers, per-account automation toggle, caps and activity log in `docs/plugins.md`. Never give plugins tier 4 (account control) or a way around those checks.
- Every user action goes through the command registry in `bonsai-core` (`commands.rs`). A button, menu item or shortcut that is not also a command in the command bar is a bug.
  - UI code calls `run(id, arg)` from `~/lib/commands/registry`. Never call a write IPC command directly from a component.
  - Exception: steps inside a dialog that a command opened (e.g. `account.add` checking, confirming or cancelling a pasted cookie) may call their IPC commands directly. They are not separate palette entries.
  - Commands that only change UI state (navigation, zoom, sidebar) register a handler with `handle(id, fn)`. Everything else goes to `run_command` in `ipc.rs`.
- Bonsai's own watchers and background jobs only notify. They never perform a write.

### Accounts and data

- Every request, cache row and piece of UI state carries an `AccountId`. Never assume a single account. Shared public data (games, items) may be shared across accounts; private data (inventory, messages, trades, chat) never is.
- Rate limits are shared across all accounts on the machine.
- Deserialization must tolerate missing and unknown fields. Unknown enum values map to `Unknown`.

### IPC (Rust side)

- `bonsai-core` is the source of truth. `bonsai` only reads the store or forwards to `bonsai-core`.
- Tauri commands run on the main thread. They take short locks or send to `bonsai-core`, nothing else. No network, no disk, no sleeping.
- Every command and event uses `#[specta::specta]` / `tauri_specta::Event` and is registered in `ipc::builder()`.
- IPC types are UI-facing views defined in `ipc.rs`, not `bonsai-core` store types. Send only what a screen needs, not the whole store.
- Ids cross IPC as `ipc::Id` (a JS number; Roblox ids fit). Use a string for anything that can exceed 2^53.
- Large or streaming data (inventories, chat, presence) uses `tauri::ipc::Channel` or a binary `tauri::ipc::Response`, not repeated full refetches.
- Images go through `thumb://` (`thumbUrl()` in `ui/src/lib/thumb.ts`). Never send image bytes or base64 over IPC.

### IPC (UI side)

- Call the backend only through `~/lib/ipc/bindings`. Never call `invoke()` by hand.
- `bindings.ts` is generated by `cargo test -p bonsai` and on every debug launch. Commit it with the Rust change that caused it.
- Render from stores. Fetch on `storeChanged` and merge with `reconcile`. A screen never waits on the network to show something: show cached data or a loading state at once.

### Solid

- Never destructure props. Read `props.x`, or use `splitProps`.
- Use `<For>`, `<Show>`, `<Switch>`, not `.map()` or ternaries in JSX.
- Shared state lives in `createStore` stores, not in signals passed between components.
- Lists that can grow past about 100 rows use `@tanstack/solid-virtual`.
- Load each screen with `lazy()` in `app/App.tsx`.

### UI components and styling

- Feature code imports components only from `~/lib/ui`. Don't install another component library.
- All colors, fonts, sizes, radii and shadows are tokens in `src/lib/ui/styles/theme.css`. To restyle the app, edit that file, not components.
- New shared components go in `src/lib/ui`, built on Kobalte, styled with a `.css` file next to the component that targets `data-component` / `data-slot` attributes inside `@layer components` and uses only theme tokens. Export it from `src/lib/ui/index.ts` and add it to the gallery at `/components`.
- Feature code uses Tailwind for layout only (flex, grid, gap, padding, size). Colors, fonts and radii come from theme tokens (`bg-surface`, `text-fg-muted`, `border-line`, `text-sm`, `rounded-md`). No hex values, no arbitrary colors.
- Fonts and icons are bundled. Nothing loads from the network.

### Modules

- One folder per feature under `src/features/`. Features never import from each other; shared code goes in `src/lib/`.

### Dependencies

- JS uses bun only. No npm, pnpm or yarn lockfiles.
- `bunfig.toml` only installs package versions at least 14 days old. Don't override it.
- Pin Rust deps in the root `Cargo.toml` `[workspace.dependencies]`.
- Add a dependency only when it removes real work, and say why in the PR.

## Adding an undocumented endpoint

Create or extend `specs/undocumented/<host>.yaml` in Swagger 2.0 form so the generator handles it like any other spec. Include:

- `host`, path, method, query and body params, response schema with only the fields we use.
- A comment with the date you captured it and the site page that calls it.

Add a replay fixture for it in the same PR.

## Testing

- Every endpoint wrapper used by the UI has a replay test with a recorded fixture under `crates/bonsai-api/tests/fixtures/`. Scrub IDs and names that could identify a real person before committing.
- Live tests (`cargo test --features live`) hit the real API with a throwaway account from `RBX_TEST_COOKIE`. They never run in CI by default.
- Domain logic (filters, sorting, state transitions) gets unit tests in `bonsai-core`.
- UI logic that is not layout (shortcut matching, list shaping) gets Vitest tests next to the file: `foo.ts` → `foo.test.ts`.

## Commands

Run from `crates/bonsai/ui/`:

| Command | What it does |
|---|---|
| `bun install` | Install JS deps |
| `bun run app` | Run the desktop app with hot reload |
| `bun run dev` | Vite only, in a browser. IPC calls fail there. |
| `bun run check` | Typecheck, Biome lint and format check, Vitest |
| `bun run fix` | Apply Biome fixes |
| `bun run tauri build` | Release build and installers |

Run from the repo root: `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.

## Platform notes

- Linux uses WebKitGTK, the slowest of Tauri's webviews. Test scrolling, animation and blur there.
- On Wayland with the NVIDIA driver, WebKitGTK crashes with "Error 71 (Protocol error)" unless `__NV_DISABLE_EXPLICIT_SYNC=1`. `main.rs` sets it. Don't use `WEBKIT_DISABLE_DMABUF_RENDERER`; it turns off GPU compositing.
- `.taurignore` keeps `tauri dev` from restarting the app when `ui/` changes. Without it, the startup bindings export restarts the app in a loop.

## Definition of done

- `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass.
- `bun run check` passes in `crates/bonsai/ui`.
- `bindings.ts` is regenerated and committed if IPC types changed.
- `docs/gaps.md` is updated if you closed or found a gap.
- `coverage.json` shows any newly used operations as used.
- No screen you touched waits on the network or shows a blank state when cached data exists.
- Every new action is a registry command with a title and keywords, and shows up in the command bar.
- PR description lists the endpoints used and links any new undocumented spec.
- Your work is committed (see below).

## Committing

- When your task is done and the checks above pass, commit your work. Don't leave it uncommitted.
- Commit only the files you changed for your task. Don't stage other people's in-progress changes (`git add -A` is usually wrong).
- Never commit to `main`. If you're on it, create a branch first.
- Write a short imperative subject line saying what changed (e.g. "Add trade list screen"), plus a body if the why isn't obvious.
- Don't push, amend or rewrite history unless asked.

## Style

- Dense, keyboard-first desktop app. Spend effort on layout and density, not decoration.
- Every action reachable without a mouse and listed in the command palette.
- Plain, short UI copy. No marketing language.
- Small PRs. One screen or one subsystem at a time.
